Large-scale scientific simulations place many objects in space, such as the particles of an [N-body simulation](https://en.wikipedia.org/wiki/N-body_simulation) in astrophysics, or the segments of the neurons of a model of brain tissue. The data of the largest simulations does not fit in the memory of one compute node. Even if each object holds only its three coordinates in double precision (24 bytes), a trillion objects take 24 TB, and 4,096 compute nodes still hold about 244 million objects (5.9 GB) each.

Imagine $$n$$ objects placed in a multidimensional space, stored across a distributed network of $$p$$ compute nodes. The problem is simple:
- how to divide the universe in such a way that each compute node gets an equal number of objects $$n/p$$? and
- how to ensure that the objects of each compute node are as close as possible to each other? and
- how to ensure that the regions of overlap of objects across compute nodes are minimal or nonexistent? 

This is a very common problem setup, known as **domain decomposition** (or spatial decomposition), and one of high importance in large-scale scientific applications. The main rationale is that a good spatial decomposition stores close objects in the same memory region (compute node), so that inter-node dependency (communication) is reduced. As objects interact mostly with the objects near them, a node needs from the other nodes mainly the objects in a thin layer around its region, its **halo** (or ghost region). Moreover, an object with volume that crosses a boundary is duplicated on both sides.

The halo and the duplicated objects both grow with the surface of the region, while the work of a node grows with the number of objects inside it. For the same number of objects, compact regions, close to squares in 2D or cubes in 3D, have the smallest surface, i.e. the lowest surface-to-volume ratio, and thus the least communication. This post compares the simplest spatial decompositions, and details a distributed algorithm for the most efficient of them.

## Slicing Layouts

The simplest spatial decomposition algorithms perform an **orthogonal spatial decomposition** (*slicing*): every cut is orthogonal to one axis, so that each slice is an axis-aligned rectangle (a box in 3D). A small note on efficiency. Slicing layout 1 incurs a lot of object duplication when objects are not points in space but have volume, and when there is a high number of slices. As an example, 16 slices of a square take 15 cuts across the whole square in layout 1, and $$3 + 3 = 6$$ in a $$4 \times 4$$ grid. For small objects spread uniformly, layout 1 then duplicates about 2.5 times as many objects. Layout 2, the **non-uniform grid** (NUG), works better by reducing cloning, yet it does not guarantee an accurate spatial decomposition, as the cuts of each dimension are shared by all slices, which may then hold different numbers of objects.

Layout 3 is the **orthogonal recursive bisection** (ORB), introduced by [Berger and Bokhari](https://doi.org/10.1109/TC.1987.1676942) in 1987 to balance the work of nonuniform problems on multiprocessors. Layout 4 is the **sort tile recursive** (STR) layout, introduced by [Leutenegger et al.](https://doi.org/10.1109/ICDE.1997.582015) in 1997 to pack the [R-trees](https://en.wikipedia.org/wiki/R-tree) of spatial databases. STR sorts the objects on the first axis and cuts them into $$S_1$$ slices with the same number of objects. It then sorts the objects of each slice on the second axis and cuts the slice into $$S_2$$ slices, and so on for each dimension.

Layouts 3 and 4 are similar, but layout 4 outperforms layout 3 in parallelism. This is because layout 3 performs a tree-based recursive bisectional decomposition (i.e. at every level of the tree it computes 2 slices), while layout 4 performs several slices at once for each of the 2 dimensions. The cuts of layout 3 are those of a balanced [k-d tree](https://en.wikipedia.org/wiki/K-d_tree), which cuts each region in two at the median of its points, along the axes in turn.

The following table details the complexity of each algorithm for $$n$$ objects, $$s$$ slices and $$d$$ dimensions (assuming sorting with an average complexity of $$n \log n$$):

As an example, take $$n = 10^6$$ objects and $$s = 16$$ slices in 2D, so that $$\log_2 n \approx 19.9$$. The single axis layout sorts the objects once, about $$20n$$ comparisons, and a $$4 \times 4$$ non-uniform grid sorts them once per dimension, about $$40n$$. A $$4 \times 4$$ sort tile recursive layout sorts them once and then sorts its 4 slices of $$n/4$$ objects, about $$38n$$, while the recursive bisection needs $$\log_2 16 = 4$$ levels, about $$74n$$, twice as much. The gap grows with the number of slices: for 1,024 slices, the 10 levels of the recursive bisection take about $$154n$$ comparisons, and a $$32 \times 32$$ sort tile recursive layout about $$35n$$.

Across these four slicing layouts, layout 4 is the most efficient: it guarantees low data duplication, allows for accurate slicing, and requires only $$d$$ (dimensions) recursive iterations, regardless of the number of compute nodes (unlike layout 3). However, its implementation in a distributed memory environment is not trivial, as no compute node can hold or sort all the objects. Possible options are:
- A histogram/binning algorithm that clusters elements in spatial bins and uses the number of elements per bin as the metric for slicing;
- A method that performs serial slicing on one compute node that holds only a sample of the data, and uses the slicing of the sampled dataset as the slicing of the final dataset.

Both options are approximate: the bins and the sample only estimate where the cuts fall, so the slices hold about the same number of objects, but not exactly the same.

## Distributed Slicing via Sort-Balance-Split

A technique published by the author in [this paper][slicing-ref], called the **Sort-Balance-Split** (SBS), implements a parallel multi-dimensional slicing based on layout 4. The algorithm follows three steps:
- The **sorting** step performs a distributed sort of all elements on a given dimension (the implementation uses a [sample sort](https://en.wikipedia.org/wiki/Samplesort));
- The **[load balancing](https://en.wikipedia.org/wiki/Load_balancing_(computing))** step equalizes the number of elements across compute nodes, which the sort leaves uneven, while respecting the initial sorting. Each rank shares its element count with all the others, and computes from the counts the global position of its elements in the sorted order. It then sends each element to the rank that holds this position after the balance, as illustrated in the following picture:

 <img width="52.4%" height="52.4%" src="{{ site.assets }}/slicing/balance.svg">

{: .caption}
Load balancing of 19 sorted elements on 3 ranks, colored by rank. The first 19 mod 3 = 1 rank holds one more element. In an MPI implementation, step 1 is one `MPI_Allgather` of the element counts, and step 2 is one `MPI_Alltoall` of the send counts followed by one `MPI_Alltoallv` of the elements. Adapted from: [An Efficient Parallel Load-balancing Framework for Orthogonal Decomposition of Geometrical Data](https://link.springer.com/chapter/10.1007/978-3-319-41321-1_5)

- The **splitting** step creates smaller networks, called **subnetworks**, from subsets of consecutive ranks of the main network. In [MPI](https://en.wikipedia.org/wiki/Message_Passing_Interface), each subnetwork is a new **communicator**, a group of ranks with its own collective calls, so that the subnetworks of a level work in parallel. The split is illustrated in the following picture:

{: .picture}
 <img width="60.2%" height="60.2%" src="{{ site.assets }}/slicing/split.svg">

{: .caption}
The split of 8 ranks into $$S_k = 2$$, $$S_k = 3$$ and $$S_k = 4$$ subnetworks of consecutive ranks, after the sort and the balance, colored by rank. The data stays in place, and each rank gets a new rank in its subnetwork. In an MPI implementation, the split is one collective operation, `MPI_Comm_split`. For $$S_k = 3$$, which does not divide the number of ranks, the subnetworks have 3, 3 and 2 ranks. Adapted from: [An Efficient Parallel Load-balancing Framework for Orthogonal Decomposition of Geometrical Data](https://link.springer.com/chapter/10.1007/978-3-319-41321-1_5)

The three steps explain the name Sort-Balance-Split. The SBS algorithm is performed recursively at every level, where each level operates on the subnetworks created by the split step of the previous level. Level $$k$$ sorts on dimension $$k$$ and splits each subnetwork into $$S_k$$ subnetworks, so that after the $$d$$ levels each rank holds one slice, and $$s = p = S_1 S_2 \cdots S_d$$. By default, the implementation picks the $$S_k$$ with the smallest sum, such as $$2 \times 2 \times 2$$ for 8 ranks and $$16 \times 16 \times 16$$ for 4,096 ranks. For objects spread uniformly in a cube, the total area of the cuts is $$S_1 + S_2 + S_3 - 3$$ times the area of a face, so the smallest sum gives the least duplication.

Each level needs eight collective calls for its three steps. The sample sort makes four: the gather of the samples, the broadcast of the splitters, and the all-to-all exchanges of the counts and of the elements. The balance makes three: the all-gather of the counts, and the all-to-all exchanges of the send counts and of the elements. The split makes one. This number does not depend on the number of objects, so that a 3D slicing takes 24 collective calls. In a network of more than 4,096 ranks, the implementation gathers the samples in two stages, through groups of 128 ranks, so that no rank receives all the $$p(p-1)$$ samples; this adds three calls per level, and the number of calls stays fixed.

This method has two advantages over existing methods: (1) a fixed number of communication steps, for any network size, input size and distribution of the data; and (2) an accurate spatial decomposition, i.e. not an approximation. However, SBS moves the objects at every level: for objects placed at random, a 3D slicing on 64 ranks ($$4 \times 4 \times 4$$) moves 98%, 94% and 75% of the objects in the sorts of its three levels. The histogram and sampling methods compute an approximate slicing first and then move each object only once: these are preferable when an approximate balance is enough.

From left to right:
1. Initial data layout;
2. The initial sorting operation sorts all elements on the first (X) dimension, without caring about the other coordinates. Data is load balanced on the X axis, so that each rank holds 4 shapes;
3. A network split divides the initial problem of 16 shapes across 4 nodes on a single network into 2 problems of 8 shapes, each on a subnetwork of 2 nodes;
4. Each subnetwork performs a distributed sort of its objects on the next axis (Y), and balances the workload;
5. A network split on the Y axis gives the final data layout, where each rank holds one slice of 4 shapes.

The original [publication][slicing-ref] evaluates SBS on 4,096 nodes of an [IBM Blue Gene/Q](https://en.wikipedia.org/wiki/IBM_Blue_Gene) supercomputer, with up to a trillion elements. There, it scales almost linearly, and it gives a better load balance in a shorter time to solution than the sampling and parallel partitioning methods of its time. Limitations, benchmarks and a more thorough analysis of the problem are available in the publication.
The `C++` implementation, with MPI, is available in <a href="{{ site.assets }}/slicing/slicing.tar.gz">slicing.tar.gz</a>.

To find more about the topic, the [Multi-Jagged](https://doi.org/10.1109/TPDS.2015.2412545) algorithm of Deveci et al. computes a layout similar to layout 4, with several cuts per dimension, and runs faster and scales better than the recursive bisection of layout 3.
